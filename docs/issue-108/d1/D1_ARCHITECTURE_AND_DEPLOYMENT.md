# Issue #108 D1 | Persistent OpenCode server and autonomous EX curation

**Implementation authority:** Central-authored at the accepted `main@47cf1cd3ed5155d2907bfd7595fec616e817712e`. This is a narrow host-local compatibility addition, not a change to the GitHub repository-root V9 guard or installed V10 ledger. The working branch/PR is review material until its exact source and host qualification are accepted.

## Root cause and selected design

The live `opencode-serve.service` starts `opencode serve` under the original `openviking-agent-run` → `flock -s --close` → `admission_exec.py` chain. Its SH lock remains held for the lifetime of the foreground server. Both the existing Graphiti curator (`post-exit-drain.py`) and OpenViking gate require EX on the same lock. Autonomous EX admission therefore starves even after a client exits.

**Selected bounded solution:** retain this known-good SH/EX admission chain and deliberately quiesce the persistent service for bounded post-exit curation. A small transparent **loopback-only ingress fence** owns the existing client endpoint `127.0.0.1:49374`; the original OpenCode service moves to a private loopback backend `127.0.0.1:49375`. No additional model server or memory store is created. The fence checks an owner-only atomic journal **synchronously before dispatching each HTTP request or WebSocket upgrade**. It tracks admitted in-flight responses/upgrades and rejects subsequent ingress with 503 while the window is fenced. No body or secret is logged.

The journal must be initialized once under the actual canonical SH flock using the explicit `idle_window.py bootstrap --config ...` command after host-source and current-server authentication. Once enabled, a deleted or malformed journal **fails closed for both ingress and backend startup**; a missing journal is never equivalent to idle.

A host-only Python coordinator, invoked by the existing curator `.service`, does this sequence:

1. Check authenticated immutable installed launcher/gate/curator source identities and actionable local curation status. Confirm the backend service and ingress fence are healthy.
2. Write a durable `preparing` journal. The fence immediately denies new requests. Wait for all previously admitted HTTP/WebSocket requests and native session executions to finish, and for the canonical scheduler/Graphiti admission observations to report idle twice across the configured quiet grace. A failed pre-stop observation clears only this unattempted journal and retries later.
3. Persist `stopping`, stop `opencode-serve.service` by its normal systemd user interface and verify **the backend process and listener are absent**. Its existing SH flock is released by normal process exit; no lockfile deletion/unlock or kernel-lock manipulation occurs.
4. Invoke the **unchanged** `post-exit-drain.py` while ingress stays fenced. It must acquire the original EX flock, perform its own scheduler/quiet grace, and hold EX through Graphiti reconciliation. The gate may obtain EX first; both original admission paths still serialize on the same lock.
5. Only on an existing wrapper-defined safe terminal result (exit 0, or autonomous technical retry exit 4 after its positive reconcile-only check) and a fresh canonical gate-idle observation, persist `starting`, restart the original OpenCode service (it re-acquires SH through the original shim), verify one private backend listener, then write `idle` to reopen ingress.
6. If the process crashes or a remote write result is unclassifiable, the journal remains non-idle and service ingress stays closed. A systemd `ExecStartPre` refuses an unsafe start even if another start is attempted. Recovery requires documented operator adjudication, **not** a blind retry or automatic resubmission.

This choice accepts **short, bounded local HTTP unavailability** during EX curation rather than modifying OpenCode request internals or running a permanent untrusted inference scheduler. In the presence of unresolved remote submissions, availability intentionally remains blocked. It does not modify the protected `appliedTurns` ledger, Graphiti ReviewStore, OpenViking spool, or databases except through the already accepted curator worker.

## D1.3/D1.4 fence-crash decoupling (independent Central review and host correction)

The source review of PR #113 found that `BindsTo=ghdev-ingress-fence.service` on the backend couples **the lifetime** of a healthy native OpenCode server to a transient proxy process. A proxy crash can consequently stop the backend and interrupt an admitted native drain, while automatically restarting the proxy alone need not restart the backend. D1.3 initially used `Requires=...` + `After=`. The disposable user-systemd host investigation proved that this still **stops/restarts** the backend on a proxy restart and does **not reliably block** backend start against a terminally failed required unit. Neither violates shell syntax, but both violate the desired lifetime and start-safety invariants. D1.4 therefore uses `Wants=ghdev-ingress-fence.service` + `After=` to pull in and order the fence at startup **without a lifetime stop/restart dependency**. A new bounded `ExecStartPre` readiness probe inside `idle_window.py check-start` verifies the existing owner-only maintenance journal is in `idle` or `starting`, that the exact managed `ghdev-ingress-fence.service` is active, and that its PID matches the healthy loopback ingress status with the correct blocked state and zero active connections. A failed or absent proxy **denies backend start**. The initial readiness wait is bounded to handle a `Type=exec` proxy that has exec'd but not yet bound the socket. An already-running backend stays alive if the proxy crashes; clients cannot reach the private backend until the proxy recovers. The proxy reuses its fail-closed journal read on recovery. No live EX/SH or native guard semantics change, and the explicit rollback still stops backend before proxy.

A fresh disposable user-systemd lifecycle proof is mandatory at the amended exact head: (a) an unexpected gateway process crash/restart retains backend PID, in-flight work and SH lease, (b) backend startup with a missing, terminally failed or incorrect-PID gateway fails the `ExecStartPre` gate, (c) starting only the backend normally starts and awaits the wanted gateway, and (d) unsafe/missing journal remains fail-closed after gateway restart. Explicit operator rollback stops backend first. This revised relationship intentionally does **not** promise backend stop propagation when the fence is administratively stopped; safety depends on fail-closed front and the private backend interface. No production cutover until these host tests pass. The existing D1.2 host regression results remain valid for unchanged Python/Node source. This correction makes no assertion that clients retain uninterrupted TCP streams during a proxy crash.

## Necessary host acceptance and potential blockers

The disposable controller and loopback proxy tests do not by themselves qualify all native OpenCode transport semantics. One bounded host campaign must check:

- OpenCode v2.3.0 HTTP/SSE/WebSocket and CLI `--server` traffic really flows through the fence, with no inference-capable direct backend callers; preserve Basic authentication and all effective guards. `/__ghdev_ingress/status` is a local diagnostic endpoint, not a second client API or source authority.
- `GET /api/session/active` on the **private** OpenCode v2.3.0 backend must return authenticated JSON `{"data":{...}}`. Upstream `v2.3.0` protocol/handler reports process-owned active foreground session drains (`{sessionID:{"type":"running"}}`), not all durable or external work. D1.2 additionally requires `GET /api/experimental/job?status=running` to return authenticated JSON `{"data":[]}` before stop, because `POST /api/session/:id/background` removes still-running backgroundable shell/image/subagent jobs from the foreground-active set. Any running job, unsupported endpoint, malformed envelope or unexpected status fails closed. The job-list API is experimental, so installed host compatibility is an explicit acceptance precondition. These two empty results are necessary but not sufficient: compare an actual asynchronous prompt and a backgrounded native shell while executing and after settlement, plus provider scheduler, ingress active count and the second quiet-grace read. The old `/session/status` is an SPA fallback and must not be used. If a prompt or background job outlives every admitted request and is missing from both this API and canonical scheduler/gate checks, activation remains blocked pending a Central-owned stronger admission boundary. API source: `anomalyco/opencode@v2.3.0`, `packages/protocol/src/groups/session.ts` and `packages/server/src/handlers/session.ts`.
- A held response or WebSocket must keep `active>0` and postpone the window; a new request after `preparing` must receive 503 and never reach the backend. Crash/restart of the fence while the journal is non-idle must remain closed. Long-lived SSE may reduce EX availability but is not reason to falsely exclude inference-capable work.
- Native session active just before the fence, candidate arrival during the quiet period, simultaneous new client, curator EX acquisition, scheduler activity, gate commit contention, worker crash/unknown remote submission, and systemd restart after an interrupted window must preserve source/at-most-once invariants. Do not simulate an actual ambiguous Graphiti write in production.
- The canonical EX drain must complete a genuine queued source path or return a typed safe SKIP/DEFER, preserve the current 397/397 target-group membership, and leave both Graphiti and OV healthy. A queued/deduped fact is not a fabricated terminal UUID. A fresh terminal source-group readback is still needed to satisfy C4 where applicable.
- Restore one healthy proxied shared service, no stale relay/port owner, original provider route, deployed V10 core digest, authentic `development-knowledge` group membership, old 128 cursors plus legitimate new ones, correct active XDG_DATA_HOME SQLite, and all rollback materials.

**Do not claim an unconditional request-level admission guarantee from this source alone.** Service-internal asynchronous work not coupled to active HTTP/SSE/WebSocket requests must be proven quiescent through the installed native status and canonical scheduler before backend stop. If the current OpenCode build cannot provide that proof, this candidate remains pre-production until a Central-owned stronger ingress/task boundary is implemented.

## D1.5 truncated upstream stream recovery

Late independent Codex review of PR #113 identified an incomplete SSE response after an OpenCode/backend crash: `IncomingMessage.pipe(res)` does not automatically close the client response on upstream abort, potentially leaving the fence `active>0` indefinitely and starving autonomous maintenance. The proxy now explicitly destroys downstream responses on upstream `aborted`, `error` or premature `close` (and on request errors after response headers). The existing downstream `close` handler releases exactly one active admission. The new real loopback regression sends one SSE event then crashes the backend socket; it requires prompt downstream disconnect, active-count release and fail-closed `preparing` behavior. Normal long-lived connected SSE remains intentionally counted and may defer maintenance; it is not forcibly closed for administrative convenience. No Python controller, systemd unit, SH/EX lock, Graphiti or model authority changes.


## D1.6 client disconnect and upgraded-socket error recovery

The second and final permitted manual Codex review of PR #113 (`8ac8ed6277ed1efd38fe011df8163475215cd74d`) identified two distinct validated proxy teardown gaps. On an established HTTP/SSE response, a downstream client disconnect released the proxy's `active` count but left the upstream backend subscription running. On a successful WebSocket upgrade, an abrupt downstream TCP RST could emit an unhandled socket `error` and crash the whole proxy. D1.6 addresses both **without** touching the journal, EX/SH locking, coordinator, units, native session handling or memory sources:

- Downstream HTTP response `close` idempotently releases admission and destroys the associated upstream request and response so abandoned SSE subscriptions do not accumulate.
- Upgraded downstream sockets receive an explicit `error` listener before any fence decision; a reset destroys the socket, which triggers the existing tunnel-close path and upstream cleanup instead of an unhandled process exception.

The focused real-loopback Node tests cover both cases and assert the proxy survives, the backend stream/tunnel closes, `active` returns to zero, and subsequent healthy requests still succeed. Reuse D1.5's prior truncated-upstream SSE regression as a complementary directional control. Exact-head host evidence and fresh Central independent review are still required. Both manual Codex requests for PR #113 have been consumed; a new request is not authorized without an explicit user override.
